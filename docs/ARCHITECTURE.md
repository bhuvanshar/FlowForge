# Architecture

## Overview
Monorepo with a single Spring Boot backend (not microservices), a React SPA, and PostgreSQL.
The backend owns workflow validation and execution; the frontend owns editing and visualization.
REST APIs live under `/api/v1`. MVP is single-user and localhost-only, structured so authentication and
multi-tenancy can be added later.

## Repository layout
`/backend`, `/frontend`, `/infra`, `/docs`.

## Backend packages (`com.flowforge`)
| Package | Responsibility | May depend on |
|---|---|---|
| `api` | Controllers, DTOs, error handling (`api.error`), path constants | `application`, `domain` |
| `application` | Use-case services and ports (interfaces such as `HealthProbe`) | `domain` |
| `domain` | Domain model and rules (`domain.workflow`, `domain.execution`), free of Spring/JPA; uses only Bean Validation annotations | nothing |
| `infrastructure` | Adapters implementing ports (DB, outbound HTTP, scheduling) | `application`, `domain` |
| `config` | Spring configuration, typed properties (`FlowForgeProperties`) | any |

Conventions: constructor injection only; DTOs at the API boundary (never entities); Bean Validation on
request DTOs; every schema change is a forward-only Flyway migration in `db/migration` (`V<n>__name.sql`);
JPA `ddl-auto=validate`; `open-in-view=false`.

## Persistence (Module 2)
Tables (Flyway `V2`–`V4`):

| Table | Purpose | Key points |
|---|---|---|
| `workflows` | current workflow definitions | `definition` JSONB; `version` = definition version; `lock_version` = optimistic lock |
| `workflow_executions` | one row per run | `workflow_snapshot` JSONB + `workflow_version`; lifecycle check constraints; `lock_version` |
| `node_executions` | one row per node run | `input`/`output` JSONB; `sequence` unique per execution |
| `webhook_triggers` (V6) | webhook registration per workflow | PK `workflow_id`; unique `webhook_id`; method/auth/input mode copied from the trigger node; `secret`; `active` |
| `schedule_triggers` (V6) | schedule registration per workflow | PK `workflow_id`; cron, time zone, policy; `next_fire_at` (partial index where active); last fire/missed/error |

V6 also adds `workflow_executions.trigger_type` (`MANUAL` default, `WEBHOOK`, `SCHEDULE`) and `scheduled_for` (set exactly for
`SCHEDULE`, check constraint) with the partial unique index `(workflow_id, scheduled_for)`.

- Foreign keys: `workflow_executions.workflow_id → workflows.id` and `node_executions.execution_id →
  workflow_executions.id`, both `ON DELETE CASCADE`. Deleting a workflow deletes its history.
- Status columns are `VARCHAR` with `CHECK` constraints, not PostgreSQL enums, so new values only need a
  migration that replaces the constraint.
- Entities live in `infrastructure.persistence` and are never exposed by the API. Aggregates reference each
  other by UUID, without JPA associations. IDs are generated by the application (`UUID.randomUUID()`).
- JSONB columns map with Hibernate `@JdbcTypeCode(SqlTypes.JSON)`. Hibernate uses Spring's `ObjectMapper`
  (`JpaJsonConfig`), so stored JSON follows the API's JSON conventions.
- Entity state-transition methods enforce the same lifecycle invariants as the database constraints.
  Orchestration is not part of this module.

### Graph validation (Module 6)
`domain.validation.GraphValidator` is framework-free and deterministic. It runs fixed passes (size, nodes, edges, connection
counts, triggers, branches, cycles via iterative DFS, reachability via BFS from the trigger, configuration) and computes the
execution order with Kahn's algorithm. It depends on two ports implemented in `infrastructure.catalog`:
`NodeTypeRegistry` (`JsonNodeTypeRegistry`, reads `node-types.v1.json`) and `ConfigurationValidator`
(`JsonSchemaConfigurationValidator`, networknt JSON Schema over `node-config.v1.schema.json` plus uniqueness rules).
`WorkflowValidationService` serves the validate endpoint; `WorkflowService` validates before activation.
In the editor, `useWorkflowValidation` re-validates the canvas (unsaved changes included) 500 ms after each content change,
ignoring superseded responses. Results are stored per node/edge in the editor store and shown as node badges/borders, red/amber
edges, a Problems panel (click to select and focus) and a problem list in the properties panel.

### Execution engine (Module 7)
```
POST /workflows/{id}/execute ─► WorkflowExecutionService (request thread)
   load ─► validate (GraphValidator) ─► plan (ExecutionPlanner) ─► executors present? ─► createQueued (snapshot + PENDING rows, 1 tx)
   ─► ExecutionStateManager.register(token) ─► executionWorkers.execute(job) ─► 202 {executionId}
executionWorkers thread ─► ExecutionEngine.run(job)
   for each plan step: skip? / cancelled? / deadline? ─► persist nodeStarted (tx) ─► node call on a node thread
   (Future.get with timeout, polling the cancellation token; interrupt on timeout/cancel) ─► persist result (tx) ─► …
   ─► executionFinished (tx) ─► unregister
```
- `domain.execution.ExecutionPlanner`: Kahn's algorithm from the trigger, ties by definition order; accepts only trees (one
  incoming edge per node, no cycles, all reachable) and throws `PlanningException` otherwise.
- `application.execution`: `NodeExecutor` SPI (+ `NodeExecutionRequest`/`NodeExecutionResult`/`NodeExecutionException`),
  `NodeExecutorRegistry` (one bean per node type), `ExecutionContext` (trigger input, outputs so far, variables, deadline,
  cancellation), `ExecutionEngine` (the loop), `ExecutionPersistence` port and its JPA `ExecutionPersistenceService` (every state
  change is its own short transaction; no transaction is ever open during a node call), `ExecutionStateManager` (in-memory owner
  of running executions and cancellation tokens; marks leftovers from a previous process as `EXECUTION_INTERRUPTED` at startup),
  `WorkflowExecutionService` (start/get/cancel).
- Threads (`ExecutionConfig`): bounded worker pool (`worker-threads`, `queue-capacity`) and a cached daemon pool for node calls,
  so workers can enforce timeouts and cancellation by interrupting the node thread.
- Shutdown (SIGTERM, `docker compose stop`): running executions get `spring.lifecycle.timeout-per-shutdown-phase` (12 s) to finish,
  then workers are interrupted and record `EXECUTION_INTERRUPTED`; anything still `QUEUED`/`RUNNING` in the database (e.g. after
  SIGKILL) is marked the same way at the next start. The drain plus Tomcat's graceful phase (open requests/SSE, also ≤ 12 s) fit
  in the compose `stop_grace_period` of 30 s. Verified end to end by `e2e/tests/failure-recovery.spec.ts`.
- One writer per execution: only its engine thread writes its rows while it is registered; cancel only flips the token.

### Built-in node executors (Module 8)
`infrastructure.nodes`: one `@Component` per node type (`ManualTrigger`, `SetVariables`, `Condition` + `Comparison`, `Transform`,
`Logger`, `HttpRequest`), all using `application.expression.ExpressionResolver` (pure JSON property lookup; grammar in
`ExpressionSyntax`, identical to the schema pattern). Execution log lines go through `ExecutionContext.log` and are persisted by the
engine after each node into `execution_logs` (Flyway V5).
`infrastructure.http`: `OutboundRequestPolicy` (allowlist, ports, non-public address ranges), `GuardedDnsResolver` (validates the
addresses the client will actually connect to), `HttpClientConfig` (Apache HttpClient 5: guarded DNS, no redirects/cookies/retries/
env proxies; watchdog that aborts requests on timeout or cancellation), `Redaction`.

### Execution history and observability (Module 9)
Backend: `ExecutionQueryService` (read side: paged, status-filtered history with per-execution node counts from one light
projection query; node runs with optional status filter), `PayloadRedactor` (applied by `ExecutionPersistenceService` before every
node input/output is stored, then the size cap). Responses derive node names and durations from the execution's own snapshot and
timestamps, so they stay stable after edits.
Frontend (`features/executions`): `ExecutionInspector` (execution order list + selected node's input/output/error/log; reused by the
editor panel and the detail page), `JsonView` (pretty JSON, truncation notice), `StatusBadge`, `useExecution` (polls every second
until terminal), `ExecutionHistoryPage` (`/workflows/:id/executions`: status filter, pagination, duration, failed node) and
`ExecutionDetailPage` (`/executions/:id`: summary, failure and affected node, inspector, execution log, cancel).
Editor: the toolbar **Run** button executes the *saved* workflow (disabled while there are unsaved changes), the bottom
`ExecutionPanel` shows the started run (or, on opening a saved workflow, its latest one), and node statuses are mirrored onto the
canvas from `runStatuses` in the store (display only, never serialized).

### Real-time updates (Module 10)
```
engine thread: persist (own tx) ──► ExecutionEventSink.publish(event) ──► ExecutionEventBroadcaster (in memory)
                                                                       │  per-execution channel, bounded queue per subscriber
SSE request:  subscribe ─► read snapshot from DB ─► virtual thread: send snapshot, then queue ─► SseEmitter ─► browser
browser:      EventSource ─► live overlay (monotonic) ─► refetch persisted result (debounced) ─► merged view
```
- The engine publishes **after** each database write (verified by a test that checks, inside the sink, that the announced status
  is already persisted) and publishing never blocks: it offers to bounded queues and drops subscribers that fall behind.
- `ExecutionEventStream` (api) runs one virtual thread per connection and never touches engine threads.
- Frontend `useLiveExecution` = REST query (truth) + SSE overlay (`liveState.ts`: pure reducers; `mergeLive` lets the further-along
  status win, persisted payloads always win after the refetch). Connection states: `connecting`, `open`, `reconnecting`
  (browser retries; a new snapshot repairs the view), `polling` (stream closed by server or unsupported: poll every second),
  `ended`/`idle`. No polling while the stream is open.
- Canvas: `runStatuses` come from the merged execution; the running node gets a blue ring, finished nodes a coloured dot; the bottom
  inspector follows the running node until the user picks another one.

### Automatic triggers (Module 11)
```
POST /api/v1/hooks/{webhookId} ─► WebhookController (bounded body read) ─► WebhookService
   lookup active registration ─► method ─► signature/token (+ replay guard) ─► JSON ─► input mapping
   ─► WorkflowExecutionService.startTriggered(WEBHOOK)            (requires ACTIVE; same prepare/queue/dispatch as manual runs)
ScheduleRunner (one daemon thread, every poll interval, started after startup recovery)
   due ids ─► per schedule: tx { lock row FOR UPDATE SKIP LOCKED ─► policy ─► prepare ─► create QUEUED run (scheduled_for)
                              ─► advance next_fire_at } ─► after commit: dispatch to a worker
```
**Lifecycle.** `WorkflowService` calls `TriggerSynchronizer.synchronize(workflow)` (implemented by
`TriggerRegistrationService`) in the transaction of every write (create, update, activate, deactivate, archive, duplicate), so
registrations always match the stored status and definition:

| Workflow state | Webhook registration (`webhook_triggers`) | Schedule registration (`schedule_triggers`) |
|---|---|---|
| saved with a webhook / schedule trigger, not ACTIVE | created on first save with a server-generated id + secret, `active = false` | none yet, or kept with `active = false` |
| ACTIVE | `active = true`, settings copied from the trigger node | `active = true`; `next_fire_at` computed from now on (re)activation and when cron/time zone change, else kept |
| trigger node replaced / removed | kept, `active = false` (id and secret survive) | `active = false` |
| INACTIVE / ARCHIVED | `active = false` | `active = false` (missed while inactive = never run) |
| permanently deleted | removed (FK cascade) | removed (FK cascade) |

An ACTIVE workflow must stay valid (activation and saves while active validate the graph), so a registration never points at a
definition that cannot run. Endpoints read only the registration tables, never the definition. Execution rows carry
`trigger_type` (MANUAL/WEBHOOK/SCHEDULE) and, for scheduled runs, `scheduled_for`.

**Duplicate prevention (schedules).** (1) Row lock with `SKIP LOCKED`: a schedule in progress is invisible to other polls.
(2) Creating the run and advancing `next_fire_at` commit together. (3) An existence check for the occurrence. (4) The partial
unique index `uq_workflow_executions_schedule_occurrence (workflow_id, scheduled_for)` rejects any second run for an occurrence,
whatever the writer. Tests: `ScheduleTriggerIT` (repeated and 6 concurrent polls, rewound `next_fire_at`, direct insert).

**Missed runs and restarts.** `next_fire_at` is persisted, so after a restart the first poll sees overdue schedules. An occurrence
handled more than `missed-run-grace` (60 s) late counts as missed: `skip` records `last_missed_at` and moves to the next future
occurrence; `runOnce` starts one run for the latest missed occurrence (`late: true`). Within the grace period (quick restart, slow
poll) the run happens normally. If the process dies after a run was committed but before a worker took it, startup recovery
(`ExecutionStateManager`, ordered before the scheduler) marks it `EXECUTION_INTERRUPTED`; the occurrence is not retried.

**Time zones.** Occurrences are computed with Spring's `CronExpression` in the schedule's zone: daylight saving time is followed;
a local time skipped by spring-forward has no run that day, a local time repeated in autumn runs twice (two instants).

### Scheduler limitations (single-instance MVP)
1. **One scheduler per database.** Duplicate runs are impossible even with several (see above), but nothing balances or fails over
   work; set `FLOWFORGE_SCHEDULER_ENABLED=false` on all but one instance if you ever run more.
2. **Polling granularity.** Due schedules are checked every `scheduler-poll-interval` (5 s): runs start up to that late, and
   several occurrences between two polls coalesce into one run (sub-5-second crons fire about every 5 s).
3. **Throughput.** At most `scheduler-batch-size` (50) due schedules per poll; runs then share the normal execution queue (503
   behaviour: a run rejected by a full queue is recorded as FAILED `EXECUTION_REJECTED`, not retried).
4. **No catch-up of every missed occurrence** (policies are `skip` and `runOnce` only) and nothing runs for time spent inactive.
5. **Clock.** Uses the server clock; a large clock jump forward is treated like downtime (missed-run policy), backwards waits.
6. **Webhook replay cache is in memory** (per process, bounded at 10 000 signatures): a restart forgets it, and the ±5 minute
   timestamp window bounds what could be replayed then. Several instances would need a shared cache.
7. **Webhook secrets** are encrypted with the credential keyring (AES-256-GCM, associated data = workflow id + webhook id;
   `WebhookSecretStore`, V8). Only on a server without a keyring are they kept in plaintext (logged as a warning); such rows,
   and rows from before V8, are encrypted at the next start with a keyring and by `POST /credentials/re-encrypt`. A secret
   that cannot be decrypted makes its webhook answer `503 webhook-unavailable` (fail closed).

### Trust boundary and security model (Module 12)
FlowForge is a **single-user, localhost-only** application without login. The trust boundary is the machine:
- The backend binds to `127.0.0.1` (containers publish ports on `127.0.0.1` only). Anyone who can open a local socket is
  trusted as the owner; do not expose ports 5173/8080 to a network.
- Browsers are the main remote attack path, so the API defends against web pages: the `Host` allowlist defeats DNS rebinding,
  cross-site writes are refused by `Origin`/`Sec-Fetch-Site` (CSRF), CORS lists exact origins, responses forbid framing and
  sniffing, and the frontend is served with a strict CSP (`script-src 'self'`, no framing).
- Webhooks (`/api/v1/hooks/**`) are the only endpoints meant for other programs; they authenticate every request themselves
  (Module 11).
- No cosmetic login was added: real authentication (users, sessions or tokens, CSRF tokens, access-control tests) is a separate
  module. The ownership model below is ready for it.

**Ownership.** `OwnerContext.currentOwnerId()` names who is acting (`local` in the MVP, `LocalOwnerContext`). Credentials and
workflows store `owner_id`. Every credential read/write is scoped to the current owner (a foreign credential is a 404); runs
resolve credentials as the **workflow's** owner (also for webhook and schedule runs), and validation flags references to
credentials the owner cannot use. Workflow queries are not filtered by owner yet; a multi-user module adds that filter and an
authenticated `OwnerContext`, plus workspace ids if needed, without schema changes to credentials.

### Credentials and encryption (Module 12)
```
API ─► CredentialService ─► CredentialTypeRegistry (fields, rules) ─► SecretCipher (AES-256-GCM) ─► credentials table
HTTP Request node ─► CredentialResolver.resolve(id, workflowOwner, nodeType) ─► decrypt ─► header ─► SecretMask.register
ExecutionEngine ─► SecretMask.mask(input/output/error/log) ─► persistence and events
```
- **Encryption**: AES-256-GCM, a fresh 96-bit nonce per encryption, 128-bit tag. Associated data
  `flowforge:credential:v1|<id>|<owner>|<type>` binds each ciphertext to its row: copied or tampered ciphertext does not decrypt
  (`CREDENTIAL_UNAVAILABLE`). The secret fields are encrypted together as one JSON document; plaintext buffers are zeroed after use.
- **Keys** live outside the database and repository: `FLOWFORGE_CREDENTIALS_KEYS` (`keyId:base64,...`) and/or
  `FLOWFORGE_CREDENTIALS_KEY_FILE` (warns if readable by others). The row stores only `key_id`. A malformed keyring stops startup;
  no keyring disables credentials (503) without affecting anything else. Integration tests generate a random key per JVM.
- **Rotation**: secret rotation (`POST /credentials/{id}/rotate`) replaces the value and increments `secret_version`; key
  rotation adds a key, makes it active, re-encrypts (`POST /credentials/re-encrypt`, one transaction) and then the old key can be
  removed. Losing all keys makes stored secrets unrecoverable by design.
- **Permitted usage**: type → node types (`usableBy`), credential → `allowedHosts`, owner → workflow owner.
- **No plaintext outward**: no API returns secrets; DTOs holding secrets override `toString`; entities never hold plaintext;
  `ResolvedCredential` exists only for one request inside the node. Value-based masking (`SecretMask`, per execution) removes
  every secret the node sent from stored node input/output, errors, logs and events, in addition to key-name redaction
  (`PayloadRedactor`, `Redaction`).

### AI integration (Module 13)
```
AiModelExecutor (infrastructure.nodes)           resolve prompts (ExpressionResolver), credential (CredentialResolver, owner of the
   │                                              workflow), header (CredentialHeaders + SecretMask), response schema (policy)
   ▼
AiChatService (application.ai)                    ONE bounded failure policy: attempts, time budget, backoff, JSON repair, usage sum
   │   ChatProviderRegistry ─ ChatProvider (port: id(), chat(ChatRequest, ChatCall))
   ▼
OpenAiCompatibleProvider (infrastructure.ai)      wire format + HTTP: guarded client, no redirects, size/time limits, watchdog
```
- **Provider abstraction.** `ChatProvider` performs one attempt and reports every failure as a typed `ChatProviderException`
  (`AUTH`, `BAD_REQUEST`, `RATE_LIMITED`, `SERVER_ERROR`, `CONNECTION`, `TIMEOUT`, `TOO_LARGE`, `BAD_RESPONSE`,
  `REFUSED_BY_POLICY`; each knows whether it is retryable). Retries, JSON handling and limits live in `AiChatService`, so a new
  provider (another wire format) is one class plus an id in the schema enum; no policy is reimplemented. The provider never sees a
  credential, only the header the node derived from it (`ChatCall.Header`, whose `toString` hides the value).
- **Secrets.** The API key exists decrypted only inside the node call, as one request header; it is registered with the run's
  `SecretMask` (stored node data, errors, logs and events are masked by value), never part of the request body, the output, the
  workflow JSON or any response, and provider error texts for 401/403 are not quoted. The frontend never receives it: the editor
  only lists credential names and ids.
- **Why the node is safe to automate.** The model's reply is data: it is parsed as JSON by a strict parser, validated against a
  schema subset, and handed to the next nodes as values; nothing is evaluated, executed, or used to choose node types, URLs or
  credentials. Model-influenced text can reach later nodes' templates (e.g. an HTTP Request URL built from `{{ input.json.url }}`),
  where the existing allowlist, address and credential-host rules still apply. Prompt injection through inserted data cannot be
  prevented by the platform; it is mitigated by schema validation, bounded retries and these downstream guards.
- **Bounds.** Requests per node ≤ 4, one time budget (≤ 300 s), prompt ≤ 100000 chars, response ≤ 1 MiB, repair echo ≤ 2000 chars,
  schema ≤ 16 KB; the engine's own node timeout (`timeoutSeconds` + 5 s), execution timeout and per-workflow execution cap
  still apply on top.
- **Tests without a provider.** Automated tests use `MockAiServer`, a scripted OpenAI-compatible server (status, headers, delay,
  body per reply, recorded requests). `AiLiveIT` is optional and skipped unless `FLOWFORGE_LIVE_AI_API_KEY` is set.

### Hardening summary (Module 12)
| Area | Measures |
|---|---|
| HTTP Request node | credentials by reference only; literal credential headers and client-managed headers rejected; credential host binding and cross-origin redirect stripping; request body ≤ 1 MiB; previous allowlist/SSRF/DNS-rebinding/redirect/size/time limits |
| Input validation | management bodies ≤ 1 MiB; JSON nesting ≤ 100, strings ≤ 2 MB, numbers ≤ 100 digits; header size 16 KB; unknown properties rejected; typed path parameters |
| CORS | exact origins only (validated at startup), explicit methods/headers, no credentials, management paths only |
| API exposure | Host allowlist, cross-site write blocking, security headers, Swagger/OpenAPI off in `prod`, actuator health without details, no whitelabel page, nginx `server_tokens off` and strict CSP |
| Execution limits | max 10 queued/running executions per workflow (503), plus worker/queue caps, node/execution timeouts, payload and log caps |
| Error handling | fixed messages for malformed JSON and bad parameters, generic 409 for constraint races, generic 500; secrets masked in node errors |
| Secret redaction | key-name redaction (history, HTTP echo, URLs), value-based masking of every credential value used, `toString` hygiene |

### Limitations of in-memory event broadcasting (single-instance MVP)
1. **One JVM only.** Events exist only in the process that runs the execution. With several backend instances a client connected
   to instance B would never see live events of an execution running on A (it would only get snapshots on reconnect). Scaling out
   needs a shared bus (PostgreSQL `LISTEN/NOTIFY`, Redis pub/sub) behind `ExecutionEventSink`/`ExecutionEventBroadcaster`, plus
   sticky routing or the same snapshot-first protocol (which already works across instances because it reads the database).
2. **Nothing is stored or replayed.** A restart loses queued events and all connections; clients reconnect and get a snapshot.
   Events between a drop and the reconnect are not replayed, they are recovered from the database state instead.
3. **No ordering guarantee across reconnects** beyond the monotonic status rule; `seq` restarts when the channel is recreated.
4. **Bounded buffers.** 256 events per subscriber and 200 connections per server; beyond that subscribers are dropped or refused.
5. **Intermediate states can be skipped** in the snapshot (a node that went RUNNING→SUCCEEDED between two reads appears only as
   SUCCEEDED). The UI treats the live view as a hint and the persisted results as final.
6. **Proxies/browsers**: an HTTP/1.1 browser allows ~6 connections per origin, so many open executions in separate tabs can
   starve other requests (HTTP/2 removes the limit). The UI opens one stream per displayed unfinished execution.

### Payload size and retention design
- **Hard caps in the database**: definition and snapshot ≤ 1 MiB each; node `input` and `output` ≤ 1 MiB each (JSON
  text); `error_message` ≤ 2000 characters. These are safety nets. The execution module must truncate or summarise
  larger payloads first, for example by storing the first N items plus a `truncated` marker, so a run is never lost
  to a constraint violation. The API module should reject oversized definitions with a Problem Detail.
- **Large payloads are TOASTed** (compressed and stored out of line) by PostgreSQL automatically. List queries should not
  select `workflow_snapshot`, `input` or `output`; detail queries load them for a single execution.
- **Retention**: `WorkflowExecutionRepository.deleteFinishedBefore(cutoff)` bulk-deletes finished executions.
  Their node executions go via the FK cascade, and the partial index `idx_workflow_executions_finished_at` serves it.
  The schedule and policy (e.g. keep 30 days or the last N per workflow, with separate rules for failures) belong
  to a later module. Delete in batches if volumes grow.
- **Errors** are stored only as `ErrorDetails` (code + sanitized message: control characters stripped, obvious
  credentials redacted, truncated). Stack traces are logged, never persisted.

## Error handling
`GlobalExceptionHandler` returns RFC 9457 Problem Details (`application/problem+json`) for every error,
with `type` = `https://flowforge.local/problems/<code>`. Unexpected errors are logged and returned without internals.

## Configuration and profiles
`application.yml` (env-var driven) plus `application-{dev,test,prod}.yml`. Default profile is `dev`. The backend
binds to `127.0.0.1` by default. Trigger settings live under `flowforge.triggers.*` (`TriggerProperties`); the test profile turns
background polling off and tests drive `ScheduleRunner.tick(instant)` directly. `spring.mvc.formcontent.filter` is disabled so no
filter consumes request bodies before the webhook endpoint applies its size and JSON rules.

### Dashboard, design system and navigation (Module 14)
- **Design tokens** live in `src/index.css` (`:root` custom properties exposed to Tailwind through `@theme`): surfaces and text,
  brand (`primary`, `primary-soft`), status tones (`success`, `warning`, `info`, `destructive`, `neutral`, each with `-soft` and
  `-foreground`), radius and shadows. Components use token classes (`bg-success-soft text-success-foreground`), never raw palette
  colours; text/background pairs meet WCAG AA. Add a tone in one place (`components/ui/tones.ts`).
- **Reusable components** (`components/ui`): `Badge`, `Notice` (alert/status, dismissible), `EmptyState`, `PageHeader`, `Skeleton`,
  `TextField`/`TextAreaField`/`SelectField` (label, hint and error wired to the control), `SegmentedControl` (labelled group of
  toggle buttons), `Dialog` and `ConfirmDialog` (native `<dialog>`: focus containment, inert background, Escape, focus return; the
  confirm button never gets the initial focus), `ActionMenu` (WAI-ARIA menu button in a portal, so cards cannot clip it).
- **Dashboard** (`features/workflows`): `WorkflowListPage` (URL state: `q`, `status`, `sort`, `page`, `view`), `WorkflowCard`,
  `WorkflowDetailsDialog` (create and rename), `useWorkflowActions` (one mutation for every action, so everything is disabled while

  fallback; they only supply defaults for the URL state) and the read-only server configuration from `GET /settings`.
- **Shell**: `AppShell` (skip link, `main` as a focus target, document title and focus move on navigation), `Sidebar` (Workflows,
  Credentials, Settings), `Header` (breadcrumb); pages other than the dashboard are lazy-loaded.

### Visual editor (Module 4)
`src/features/editor`: `WorkflowCanvas` (`@xyflow/react`), `WorkflowNode` (reusable custom node), `NodePalette`,
`EditorToolbar`, `PropertiesPanel` (node settings, Module 5; trigger status, Module 11) and `ExecutionPanel` (live run inspector, Modules 9–10), `EditorPage` (load/save wiring).
State lives in one Zustand store (`editorStore.ts`): nodes, edges, workflow metadata, `lockVersion`, undo/redo stacks
(max 100 snapshots), and a saved-content signature that defines "dirty" (name, description and graph; not viewport or
selection). Undo steps are created per add, connect, delete and completed drag. Deleting goes through the store (Delete or
Backspace, toolbar), not React Flow, so nodes, edges and history stay consistent.

#### Node configuration framework (Module 5)
`src/features/editor/config`: a schema-driven form system. Each node type is one `NodeConfigDefinition` (`definitions.ts`): a Zod
form schema, declarative `fields` (text, textarea, select, json, list), `defaultConfiguration`, and `toFormValues` /
`toConfiguration` converters between form state and the persisted `configuration`. `NodeConfigForm` renders any definition with
React Hook Form (`ConfigFields.tsx`), so a new node type needs a definition and catalog entry, not new UI code. `registry.ts`
exposes `validateNodeConfiguration` (form rules plus a lossless round-trip check, which mirrors the strict backend schema).
Unapplied edits live in the editor store as per-node `drafts`: they survive switching nodes, count as unsaved changes, and Save
applies valid drafts or refuses to save while one is invalid. Applying a configuration is one undo step. Nodes whose
configuration is invalid show a warning icon. Unknown node types get a read-only JSON view and are preserved unchanged.

Routing uses a data router (`routes.tsx`, `createBrowserRouter`): `/` workflow list, `/workflows/new` and
`/workflows/:id` editor. Unsaved changes trigger `beforeunload` and a confirm dialog (`useBlocker`) on in-app navigation.
Leaving the editor resets its store; reopening fetches the server version.

## Infrastructure
`infra/docker-compose.yml`: PostgreSQL (named volume, healthcheck) always; backend and frontend (nginx, proxies `/api`)
under the `app` profile. All host ports bind to `127.0.0.1`.
Images: multi-stage builds on digest-pinned bases (Maven/Temurin 21 → JRE 21 Alpine, non-root; Node 22 → nginx 1.27). The
backend resolves Maven dependencies from Central only (`backend/.mvn/settings.xml`). Operations: see `DEPLOYMENT.md`.
